# twitch-rag

База знаний по трансляциям Twitch для ИИ-ассистентов. Сервис следит за одним
каналом, разбирает каждую новую запись эфира в связный документ, разбитый на
разделы, и отдаёт знания программным клиентам через HTTP и через MCP.

Подробная спецификация, архитектура и обоснования решений — в
[`specs/001-stream-archive-rag/`](./specs/001-stream-archive-rag/).

## Как это работает

Основной процесс — Cloudflare Worker: расписание раз в час находит новую
запись, запускает разбор через Workflow (распознавание речи → составление
документа → индексация), отвечает на запросы знаний и обслуживает MCP-сервер
на `/mcp`. Скачивание записи и нарезка звука — единственное, что нельзя
сделать в изоляте V8, — выполняется в отдельном боксе Upstash.

```
Cloudflare Worker              Upstash Box                 Хранилища
───────────────────           ───────────────              ─────────────
расписание раз в час  ───────▶ yt-dlp + ffmpeg              R2 (аудио, минуты)
Workflow: распознать          выгрузка кусков в R2  ───────▶
  → составить документ  ◀──── сигнал "можно начинать"
  → проиндексировать                                        Upstash Vector
                                                              (разделы для поиска)
/api/knowledge/search                                        Upstash Blob
/mcp (без авторизации)                                       (документы целиком)
                                                               Upstash Redis
страница владельца ────────────────────────────────────────▶ (реестр, read-only
  (читает список трансляций напрямую из Redis)                для браузера)
```

Расшифровка не хранится — только структурированный документ, разделы в
векторной базе и запись в реестре.

## Разбор документа

Что изменилось против первого замысла ([спецификация 002](./specs/002-document-quality/)):

- документ — не сжатый пересказ, а запись сказанного: расшифровка подаётся модели
  целиком, выбрасывается только неречевое, ослышки и участки, распознанные как чужая
  речь, восстанавливаются по звучанию и смыслу, а не переносятся в текст;
- ответ модели приходит по строгой схеме (`src/shared/document-schema.ts`), у раздела
  есть заголовок, текст и время начала и конца; системная инструкция живёт отдельным
  модулем (`src/shared/prompt.ts`) и правится независимо от кода запроса;
- имя документа вырабатывается отдельным запросом по содержанию эфира, а заголовок
  трансляции с площадки в разборе, в показе и в выдаче не участвует вовсе;
- владелец один раз описывает стримера в разделе управления — сведения уходят в
  системную инструкцию;
- любую известную трансляцию можно разобрать заново (`POST /api/streams/:vodId/reparse`),
  прежние знания при неудаче остаются на месте.

### Как проверить качество документа

Стенд замеров прогоняет настоящую расшифровку через ту же инструкцию и тот же запрос,
что и разбор, и сохраняет документ, расход и признак остановки:

```bash
# расшифровка участка записи (≈10 минут, ≈0,1 $)
bun specs/002-document-quality/research/scripts/transcript.ts --vod <id> --from 20:00 --to 90:00

# замер (доли цента за проход)
bun specs/002-document-quality/research/scripts/measure.ts \
  --transcript <метка> --part-minutes 30 --variants A --tag <метка прогона>
```

Что было измерено и что из этого следует — в
[`research/results.md`](./specs/002-document-quality/research/results.md); там же
разобрано, почему разбор перешёл на другую модель. Приёмка — по сценариям
[`quickstart.md`](./specs/002-document-quality/quickstart.md).

## Развёртывание

Нужны `bun` ≥ 1.4 и авторизованные `wrangler`, `upstash`, `box`.

```bash
cp .env.example .env    # заполнить значениями из раздела ниже
bun install
bun run build           # интерфейс в dist
wrangler deploy         # Worker, Workflow, статика
```

Секреты на сервере ставятся `wrangler secret put <ИМЯ>` для каждого значения
из `.env.example`, кроме `BUN_PUBLIC_*` — те попадают в сборку интерфейса как
публичные значения.

Прогон в боксе разворачивается отдельно от Worker — команды и порядок в
[`plan.md`, раздел И4](./specs/001-stream-archive-rag/plan.md#и4-развёртывание).

Полный порядок первого запуска, включая создание внешних ресурсов, — в
[`plan.md`, раздел И5](./specs/001-stream-archive-rag/plan.md#и5-первый-запуск).
Сценарии проверки работоспособности каждой части — в
[`quickstart.md`](./specs/001-stream-archive-rag/quickstart.md).

## Разработка

```bash
bun test              # модульные и контрактные тесты
bun run typecheck      # проверка типов Worker и остального кода отдельно
wrangler dev           # локальный запуск Worker
```

Типы проверяются двумя конфигурациями (`tsconfig.json` и
`tsconfig.worker.json`): в изоляте Cloudflare Workers нет DOM, а в браузере и
боксе — нет типов Workers. Совместное присутствие обоих наборов типов дало бы
двойные объявления `fetch`, `Response` и подобных.

### Вайбкодинг

Разработка:
1. `/speckit-specify` - написать спецификацию и продумать функцию
2. `/speckit-plan` - продумать реализацию и написать план
3. `/speckit-tasks` - нарезать на задачи
4. `/speckit-implement` - выполнить
5. `/speckit-converge` - проверить, что все выполнено

## Подключение ассистента

Публичный MCP-сервер без авторизации:

```json
{
  "mcpServers": {
    "twitch-knowledge": { "type": "http", "url": "https://<адрес сервиса>/mcp" }
  }
}
```

Готовая инструкция с фактическим адресом — на странице сервиса.
