# Implementation Plan: Обрывки трансляций не берутся в разбор

**Branch**: `003-min-stream-duration` | **Date**: 2026-09-19 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/003-min-stream-duration/spec.md`

## Summary

Правило «почему запись не берём в работу» получает нижнюю границу длительности: записи
короче трёх минут разбору не подлежат. Правило остаётся в одном месте — `skipReason` в
`src/shared/twitch.ts`, рядом с двумя нынешними причинами; прежняя причина о нулевой
длительности растворяется в новой, потому что ноль секунд короче трёх минут.

Часовой отбор получает проход, помечающий короткие записи пропущенными до выбора
очередной записи к разбору. Без него восемь обрывков в архиве отняли бы восемь часов у
настоящих эфиров: за один запуск проверки берётся одна запись. Запуск разбора сохраняет
проверку у себя, поэтому ручное добавление и любой будущий путь получают тот же отказ.

Ответ на ручное добавление перестаёт выдавать пропуск за начатый разбор: сегодня он
отвечает «Запись принята в обработку» независимо от исхода, и для короткой записи это
неправда.

Работы в боксе нет, программа конвейера не меняется, новых внешних ресурсов не заводится.

## Technical Context

**Language/Version**: TypeScript; Bun 1.4 — сборка, тесты, запуск вне Worker; среда
исполнения — V8-изолят Cloudflare Workers

**Primary Dependencies**: без изменений и без добавлений. Затрагиваются `@upstash/redis`
(запись в реестр), React 19 + shadcn/ui (текст исхода на странице)

**Storage**: Upstash Redis — реестр. Меняется только содержимое записи: состояние
`skipped` и текст причины. Схема хранения, поля и ключи остаются прежними

**Testing**: `bun test` — модульные проверки правила длительности и часового отбора;
контрактные проверки Worker через `wrangler dev`; ручная проверка по
[quickstart.md](./quickstart.md)

**Target Platform**: Cloudflare Workers (бесплатный тариф) + статическая страница
владельца. Бокс Upstash не затрагивается

**Project Type**: веб-сервис

**Constraints**: за один запуск часовой проверки берётся одна запись к разбору; архив
просматривается страницами по 20 записей, не более 5 страниц, до первой известной
записи. Проверка не должна израсходовать запуск на обрывок. Пределы бесплатного тарифа,
в которые обязан уложиться запуск: 50 обращений к внешним службам на запуск и 10 мс
процессорного времени на запуск по расписанию
([документация Cloudflare](https://developers.cloudflare.com/workers/platform/limits/)).
По подсчёту по коду сегодняшняя проверка тратит около пятнадцати обращений, проход
добавляет по одному на короткую запись

**Scale/Scope**: сегодня в архиве канала 8 обрывков из 35 записей; дальше — единицы в
год, по одному на неудавшийся запуск эфира

## Решения

### 1. Признак короткой записи — в `skipReason`, а не отдельной проверкой

`skipReason(video)` сегодня отвечает на вопрос «почему эту запись не берём» и уже знает
две причины: доступна не всем зрителям и нулевая длительность. Порог становится третьим
условием того же ответа. Отдельная функция рядом означала бы два места, которые надо
править вместе, — а расхождение между ними и есть тот случай, ради которого FR-007
требует одного признака.

Проверка при этом спрашивается в двух точках: в часовом проходе пометки и в
`startStreamIngest`. Первая нужна, чтобы короткая запись не занимала очередь; вторая —
чтобы её нельзя было провести мимо правила другим путём (ручное добавление, повторный
разбор, путь, которого ещё нет).

### 2. Короткие записи помечаются до отбора, а не когда до них дойдёт очередь

`selectNextVideo` возвращает **одну** запись за запуск, и проверка идёт раз в час. Если
короткие записи помечать только тогда, когда они становятся самой ранней необработанной,
каждый обрывок съедает час, в который не разбирается настоящий эфир: восемь обрывков —
восемь часов задержки. Поэтому в часовой проверке появляется проход, который помечает
короткие записи из просмотренной части архива, и только после него выбирается запись к
разбору.

Проход подчиняется тому же правилу, что и отбор: он смотрит только на записи, появившиеся
после подключения канала (FR-003). Прошлые эфиры в работу не берутся вовсе — их добавляет
владелец, — и записывать их пропущенными значило бы завести в список три десятка записей,
которых там никто не ждёт. Сегодня после подключения канала коротких записей нет, поэтому
проход не пишет ничего: он начинает работать с первого же неудавшегося запуска эфира.

Побочное следствие: записи, доступные только подписчикам, тоже помечаются сразу, а не
когда до них дойдёт очередь. Конечное состояние то же (FR-006), меняется только момент,
и по времени это выигрыш, а не потеря.

### 3. Причина о нулевой длительности растворяется

Ноль секунд короче трёх минут, поэтому отдельное условие для него становится
недостижимым, а текст «У записи нулевая длительность — разбирать нечего» — недоступным.
Условие и текст удаляются в той же правке (принцип IV конституции: мёртвый код уходит
там, где стал ненужным).

### 4. Ответ на добавление называет исход

`handleAddStream` сегодня всегда отвечает `202 { status: "processing" }`, даже когда
`startStreamIngest` записал запись пропущенной и разбор не начинался. Для короткой
записи это прямо противоречит FR-005, и заодно это неправда про запись, доступную только
подписчикам. `startStreamIngest` начинает возвращать исход, а точка доступа — отвечать по
нему: разбор начат — `202` и `processing`, запись не взята — `200`, `skipped` и причина.
Разделение по коду ответа, а не только по полю `status`, выбрано затем, чтобы клиент, не
читающий тело, не считал пропуск начатой работой.

То же самое у повторного разбора: он идёт через тот же запуск и сегодня отвечает так же
безусловно. Правка одна на оба пути — иначе повторный разбор короткой записи обещал бы
работу, которой не будет.

На странице подпись под формой показывается по исходу. Пропуск — не успех и не ошибка,
поэтому у подписи появляется третий вид, нейтральный по цвету; показывать отказ зелёным
значило бы утверждать, что запись принята.

### 5. Текст причины

Причина пропуска видна владельцу в списке пропущенных, поэтому формулируется как
остальные: что случилось и почему разбора не будет.

> Запись короче трёх минут — разбирать в ней нечего.

Порог в тексте назван числами владельца («три минуты»), а не секундами: список читает
человек.
