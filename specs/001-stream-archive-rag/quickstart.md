# Проверка работоспособности

**Дата**: 2026-09-13 | **План**: [plan.md](./plan.md) | **Контракты**: [knowledge-api.md](./contracts/knowledge-api.md), [mcp-server.md](./contracts/mcp-server.md)

Сценарии ниже проверяют, что функция действительно работает, а не только собирается.
Порядок важен: каждый следующий опирается на предыдущий.

## Предварительные условия

В системе должны быть `bun` ≥ 1.4, `yt-dlp`, `ffmpeg`:

```bash
bun --version && yt-dlp --version && ffmpeg -version | head -1
```

Нужны учётные данные: приложение Twitch (client id и secret), ключ OpenAI, индекс Upstash
Vector и бакет Upstash Blob. Создание индекса и бакета:

```bash
upstash login
upstash vector create --name twitch-knowledge --region eu-west-1 \
  --index-type DENSE --dimension-count 1536 --similarity-function COSINE
upstash blob create --name twitch-audio --visibility private
```

Значения из ответов переносятся в `.env` по образцу `.env.example`. Файл `.env` не
коммитится; Bun загружает его сам.

```bash
bun install
bun dev
```

Ожидается: сервер поднялся, в консоли адрес интерфейса, ошибок при старте нет.

## Проверка 0. Зависимости и доступы

```bash
curl -s localhost:3000/api/health | jq
```

**Ожидается**: `status: "ok"` и `ok` у каждой проверки (`sqlite`, `vector`, `blob`,
`openai`, `ytDlp`, `ffmpeg`).

**Отдельно проверить путь ошибки**: временно убрать `OPENAI_API_KEY` и перезапустить.
Ожидается `status: "degraded"`, понятное сообщение в интерфейсе и отказ запускать
обработку — а не падение процесса.

## Проверка 1. Знания по одной записи (US1, приоритет P1)

Главный сценарий продукта.

1. В интерфейсе указать канал (или `PUT /api/channel` с `{"login": "..."}`).
2. Добавить конкретную запись вручную:

```bash
curl -s -X POST localhost:3000/api/streams \
  -H 'content-type: application/json' \
  -d '{"url":"https://www.twitch.tv/videos/<VOD_ID>"}' | jq
```

**Ожидается**: 202 и статус `discovered`; в интерфейсе трансляция появляется сразу, дальше
последовательно проходит `downloading → transcribing → structuring → indexing → ready`, и
на каждом этапе виден прогресс. Для четырёхчасовой записи весь путь занимает не больше двух
часов (SC-005).

3. Спросить знания по теме, которая на записи точно обсуждалась:

```bash
curl -s -X POST localhost:3000/api/knowledge/search \
  -H 'content-type: application/json' \
  -d '{"query":"<тема, звучавшая на стриме>","topK":5}' | jq
```

**Ожидается**: `found: true`, документы отсортированы по `score`, у каждого есть `topic`,
связный `text`, `stream.title`, `publishedAt` и ссылка с таймкодом.

**Как проверить качество, а не только формат**:

- открыть `stream.url` из первого результата — речь по теме должна звучать не далее чем
  через 10 секунд от начала (SC-003);
- прочитать `text`, не открывая запись: он должен быть понятен сам по себе, без «как я
  говорил выше» и местоимений без антецедента (SC-004, FR-014);
- сверить утверждения документа с тем, что реально сказано, — выдуманного быть не должно
  (FR-016, SC-003).

4. Спросить то, чего на стриме не было:

```bash
curl -s -X POST localhost:3000/api/knowledge/search \
  -H 'content-type: application/json' -d '{"query":"рецепт борща"}' | jq
```

**Ожидается**: 200, `found: false`, пустой `documents`, сообщение «В базе знаний нет
сведений по этому вопросу» — не ошибка и не случайная выдача (FR-024).

5. Проверить формулировку другими словами: задать тот же вопрос синонимами. Ожидается тот
же документ в выдаче — поиск по смыслу, а не по словам (FR-021).

## Проверка 2. Автоматическое пополнение (US2, P2)

1. Убедиться, что канал указан и `watchFrom` выставлен.
2. Дождаться появления новой записи на канале либо сдвинуть `watchFrom` назад в настройках
   и дождаться срабатывания планировщика (раз в 15 минут).

**Ожидается**: запись появляется в списке со `source: "auto"` и проходит весь путь без
ручных действий (FR-002).

3. Дедупликация: дождаться следующего опроса.

**Ожидается**: уже обработанная запись повторно не ставится в очередь, дубликатов
документов не появляется (FR-005). Проверяется по `document_count` и по числу результатов
на тот же запрос.

4. Устойчивость к перезапуску: во время этапа `transcribing` остановить процесс (Ctrl+C) и
   запустить снова.

**Ожидается**: трансляция возвращается в очередь и дообрабатывается, ранее готовые
трансляции не пострадали, временные объекты не осиротели (FR-031, SC-009).

## Проверка 3. Наблюдение и ошибки (US3, P3)

1. Добавить заведомо недоступную запись:

```bash
curl -s -X POST localhost:3000/api/streams \
  -H 'content-type: application/json' -d '{"vodId":"000000000"}' | jq
```

**Ожидается**: статус `failed`, код `vod_unavailable`, человеческое сообщение с подсказкой;
очередь продолжает работать с остальными записями.

2. Нажать «Перезапустить» на упавшей записи — обработка стартует заново, счётчик попыток
   обнулён (FR-030).
3. Открыть карточку готовой трансляции: видны журнал этапов и список извлечённых документов
   с темами и таймкодами.
4. Ввести пробный запрос в интерфейсе.

**Ожидается**: те же документы и в том же порядке, что вернул HTTP API — интерфейс
показывает ровно то, что получит ИИ (FR-034).

5. Наблюдать прогресс: во время обработки страница обновляется без перезагрузки (FR-029).

## Проверка 4. Управление базой (US4, P4)

1. Удалить трансляцию:

```bash
curl -s -X DELETE localhost:3000/api/streams/<VOD_ID> | jq
```

**Ожидается**: возвращено число удалённых документов; повторный поиск по её теме больше не
находит эти документы (FR-032).

2. Запустить переобработку готовой трансляции (`POST /api/streams/<VOD_ID>/retry`).

**Ожидается**: пока идёт переобработка, поиск возвращает прежние документы; после
завершения — новые; смеси старых и новых нет (US4, сценарий 3). Важно: переобработка — это
полный цикл со скачиванием, потому что расшифровка не хранится; запись старше срока
хранения Twitch переобработать нельзя, интерфейс предупреждает об этом заранее.

## Проверка 5. Подключение к ИИ через MCP

Добавить сервер ассистенту (для Claude Code — в `.mcp.json` или через `claude mcp add`):

```json
{
  "mcpServers": {
    "twitch-knowledge": {
      "command": "bun",
      "args": ["run", "src/mcp/server.ts"],
      "cwd": "/путь/к/проекту"
    }
  }
}
```

**Ожидается**: ассистент видит инструменты `search_knowledge` и `knowledge_stats`; на
вопрос по теме канала он сам вызывает поиск и отвечает с опорой на документы, называя дату
эфира; на вопрос вне базы — сообщает, что сведений нет, вместо выдумки.

## Проверка 6. Нагрузка и параллельность

1. Запустить обработку трансляции и одновременно слать запросы знаний.

**Ожидается**: ответы приходят, время ответа не вырастает более чем вдвое (SC-007), отказов
нет (FR-026).

2. Замерить время ответа на прогретой базе:

```bash
for i in $(seq 1 10); do
  curl -s -o /dev/null -w '%{time_total}\n' -X POST localhost:3000/api/knowledge/search \
    -H 'content-type: application/json' -d '{"query":"тест"}'
done
```

**Ожидается**: медиана меньше 1 секунды (SC-002).

## Проверка 7. Чистота хранилищ

После завершения обработки:

```bash
upstash blob list   # или GET /api/health, поле temporaryObjects
```

**Ожидается**: временных объектов обработанной трансляции не осталось; на диске нет
недоудалённых медиафайлов; расшифровка не сохранена нигде — ни в SQLite, ни в Blob, ни в
Vector.

## Автоматические тесты

```bash
bun test              # модульные и контрактные
bun run build         # сборка проходит без ошибок
```

Сквозная проверка конвейера выполняется на коротком фрагменте записи (`--download-sections`
на 2 минуты), чтобы не тратить минуты распознавания на каждый прогон.
