## Phase 3: User Story 1 — ИИ получает знания о содержании стримов (P1) 🎯 MVP

**Проверка отдельно от остальных**: добавить конкретную запись вручную, дождаться
документа, задать вопрос по обсуждавшейся теме и получить разделы целиком, с датой,
категорией и ссылкой на момент (проверки 1, 2 и 5 в quickstart.md).

**Примечание**: ручное добавление записи (FR-004, формально US4) входит в эту фазу —
без него историю нельзя проверить отдельно.

и убедиться, что запись берётся в работу сама, второй запуск расписания ничего не
дублирует, а запись для подписчиков помечается пропущенной (проверка 3 в quickstart.md).

- [X] T052 [US2] Реализовать `src/worker/schedule.ts`: раз в час — получить список записей канала, вычесть по реестру разобранные и пропущенные, взять самую раннюю необработанную и запустить прогон; за один запуск берётся одна запись, чтобы не съедать квоту процессорного времени бокса

## Зависимости и порядок

### По фазам

- **Phase 1 (подготовка)** — начинается сразу
- **Phase 2 (основание)** — после Phase 1; **блокирует все истории**
- **Phase 3 (US1)** — после Phase 2
- **Phase 4 (US2)** — после Phase 2; опирается на конвейер из US1 при реальной проверке, но пишется независимо
- **Phase 5 (US3)** — после Phase 2; данные для списка берёт из реестра, заполняемого US1
- **Phase 6 (US4)** — после Phase 2; удаление опирается на адаптеры из Phase 2
- **Phase 7 (отделка)** — после нужных историй

### Внутри Phase 3

T031 → T032 → T033 → T034 → T035 (прогон в боксе идёт цепочкой: метаданные, нарезка, выгрузка, точка входа)

T036 → T037 → T038 → T039 → T040 → T041 (шаги обработки выстроены по конвейеру)

T043 → T044 → T045, затем T046 → T047 → T048 (MCP вызывает тот же сервис поиска)

### Параллельные возможности

- T005–T009 в подготовке — разные файлы
- T010–T014 — создание ресурсов в разных сервисах
- T017–T020, T022–T025 — независимые модули `shared/` (T021 `registry.ts` пишется отдельно, на нём завязаны T026 и далее)
- T029, T030, T049, T050, T058, T069 — тесты в разных файлах
- T060, T061, T063, T064 — компоненты интерфейса
- После Phase 2 три истории можно вести параллельно разными людьми

## Порядок поставки

1. Phase 1 + Phase 2 → основание готово, `/api/health` отвечает
2. **Phase 3 (US1) → остановиться и проверить**: одна запись разобрана, ассистент получает знания — это MVP
3. Phase 4 (US2) → база растёт сама
4. Phase 5 (US3) → владелец видит содержимое и подключает ассистента
5. Phase 6 (US4) → управление содержимым
6. Phase 7 → замеры, проверки, публикация

Каждая история добавляет ценность, не ломая предыдущие.
