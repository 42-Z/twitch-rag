# Feature Specification: База знаний канала по записям стримов

**Feature Branch**: `001-stream-archive-rag`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "Я хочу создать приложение, которое скачивает каждый стрим с определенного канала, расшифровывает его через whisper, структурирует через llm, и сохранаяет в векторную базу данных, чтобы можно было делать RAG векторный поиск"

**Уточнения (2026-09-12)**: потребитель знаний — внешний ИИ-ассистент, а не человек; в базе знаний хранятся структурированные документы, а не куски расшифровки; отслеживается один канал; автоматически обрабатываются только новые трансляции.

**Уточнения (2026-09-14)**: модель читает расшифровку целиком и пишет связный документ о трансляции, разбитый на разделы; в поиск идут разделы этого документа; каждый фрагмент знаний снабжается категорией трансляции на момент разговора; сам документ доступен для чтения целиком; доступ к знаниям публичный, без авторизации; записи, доступные только подписчикам, пропускаются.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ИИ получает знания о содержании стримов (Priority: P1)

Внешний ИИ-ассистент, отвечая своему пользователю, обращается к сервису с вопросом по теме канала и получает разделы документов: связные тексты о том, что обсуждалось на стримах, с датой эфира, категорией и ссылкой на момент записи. Ассистент использует их как знания и может сослаться на конкретный момент разговора.

**Why this priority**: Ради этого существует сервис. Одна разобранная трансляция и работающая выдача знаний уже дают ассистенту то, чего у него не было.

**Independent Test**: Проверяется на одной разобранной трансляции: отправить запрос по теме, которая на ней обсуждалась, и убедиться, что пришли разделы, точно передающие сказанное, понятные без просмотра записи и снабжённые ссылкой на момент.

**Acceptance Scenarios**:

1. **Given** в базе знаний есть документ хотя бы одной трансляции, **When** клиент отправляет запрос по обсуждавшейся теме, **Then** возвращается упорядоченный по релевантности набор разделов с текстом, темой, названием и датой трансляции, категорией и временной меткой.
2. **Given** запрос сформулирован иначе, чем звучало на стриме, **When** он отправлен, **Then** нужные разделы всё равно находятся по смыслу.
3. **Given** найден подходящий фрагмент, **When** формируется ответ, **Then** клиент получает раздел целиком, а не обрезанный фрагмент.
4. **Given** в базе нет сведений по теме запроса, **When** запрос отправлен, **Then** сервис возвращает пустой результат с явным признаком «знаний нет».
5. **Given** клиент ограничил выборку диапазоном дат или категорией, **When** запрос отправлен, **Then** ограничения соблюдаются.

---

### User Story 2 - База пополняется новыми стримами сама (Priority: P2)

Оператор один раз указывает канал. Дальше сервис сам замечает появление записи нового эфира, разбирает её и добавляет знания. Знания ИИ-ассистента обновляются без участия человека.

**Why this priority**: Превращает разовую обработку в постоянно растущую базу знаний.

**Independent Test**: Проверяется на канале с недавно появившейся записью: без действий человека трансляция должна быть разобрана, а её разделы — начать находиться по запросу.

**Acceptance Scenarios**:

1. **Given** канал указан, **When** на нём появляется запись нового эфира, **Then** сервис берёт её в работу без участия человека.
2. **Given** трансляция уже разобрана, **When** сервис снова проверяет канал, **Then** повторная обработка не запускается и дубликаты не появляются.
3. **Given** запись доступна только подписчикам, **When** сервис пытается её взять, **Then** она помечается как пропущенная с указанием причины и больше не берётся в работу.
4. **Given** обработка прервалась из-за сбоя, **When** сервис возобновляет работу, **Then** трансляция дообрабатывается, а ранее готовые знания не теряются.
5. **Given** эфир идёт прямо сейчас, **When** сервис проверяет канал, **Then** растущая запись этого эфира не берётся, а берётся после его окончания — целиком, а не обрывком.

---

### User Story 3 - Человек видит, что знает база (Priority: P3)

Владелец открывает страницу сервиса и видит, какие трансляции разобраны, какие документы получились и как подключить базу знаний к своему ИИ-ассистенту. Документ любой трансляции можно открыть и прочитать целиком.

**Why this priority**: Без этого невозможно понять, что в базе есть, и невозможно ею воспользоваться — инструкция по подключению нужна до первого запроса ассистента.

**Independent Test**: Проверяется на разобранном архиве: список трансляций соответствует действительности, документ открывается и читается, инструкция позволяет подключить ассистента и получить ответ.

**Acceptance Scenarios**:

1. **Given** несколько трансляций разобрано, **When** владелец открывает страницу, **Then** он видит их список с названием, датой эфира, категориями и числом разделов.
2. **Given** трансляция разобрана, **When** владелец открывает её документ, **Then** отображается связный текст о стриме с разделами и временными метками.
3. **Given** запись была пропущена, **When** владелец смотрит список, **Then** он видит её среди пропущенных с указанием причины.
4. **Given** владелец хочет подключить ассистента, **When** он открывает страницу, **Then** на ней есть готовая инструкция с адресом сервиса.
5. **Given** владелец открыл любой раздел панели, **When** он передаёт ссылку на него, **Then** раздел открывается по этой ссылке у того, кому она передана.
6. **Given** владелец хочет знать, как обращаться к базе из своего кода, **When** он открывает справочник, **Then** он видит адреса запросов, примеры и коды ошибок.
7. **Given** токен владельца не введён или неверен, **When** владелец открывает раздел управления, **Then** он видит только поле ввода токена, а управляющие поля скрыты.

---

### User Story 4 - Управление содержимым базы (Priority: P4)

Владелец удаляет из базы трансляцию, которая не должна влиять на знания ассистента, либо добавляет вручную запись, которая не попала в автоматическую обработку.

**Why this priority**: Требуется при эксплуатации, но не влияет на получение первой ценности.

**Independent Test**: Проверяется на разобранной трансляции: после удаления её разделы перестают приходить в ответах, а состав других трансляций не меняется.

**Acceptance Scenarios**:

1. **Given** трансляция есть в базе, **When** владелец её удаляет, **Then** её разделы перестают появляться в результатах запросов, а документ — в списке.
2. **Given** запись не попала в автоматическую обработку, **When** владелец добавляет её вручную по адресу, **Then** она проходит тот же путь, что и новая.

---

### Edge Cases

- Запись эфира удалена, приватна или доступна только подписчикам — обработка завершается с понятной причиной, очередь не останавливается.
- Очень длинная трансляция (8–12 часов) — разбирается целиком, документ пишется по частям, связность между частями сохраняется.
- Участки записи заглушены правообладателем, содержат только музыку или тишину — разделы по ним не создаются.
- Стример менял категорию несколько раз за эфир — каждый раздел получает ту категорию, которая была в его момент времени.
- Одна и та же тема обсуждалась на нескольких стримах — клиент получает разделы разных трансляций с их собственными датами.
- Канал долго не выходил в эфир — это не ошибка.
- Внешние сервисы недоступны или исчерпан лимит — трансляция остаётся необработанной и берётся в работу позже.
- Запрос приходит во время разбора новой трансляции — ответ выдаётся по уже готовым знаниям без ожидания.
- Пустой или бессмысленный запрос — явный признак отсутствия знаний, а не случайная выборка.
- Публичным адресом сервиса пользуется посторонний — объём его обращений ограничен, работа для владельца не нарушается.

## Requirements *(mandatory)*

### Functional Requirements

**Источник и отбор записей**

- **FR-001**: Система MUST хранить настройку одного отслеживаемого канала между запусками.
- **FR-002**: Система MUST самостоятельно обнаруживать появление записей новых эфиров отслеживаемого канала.
- **FR-003**: Система MUST автоматически обрабатывать только трансляции, появившиеся после подключения канала; прошлые — только по явному указанию владельца.
- **FR-039**: Система MUST брать в автоматический разбор только записи завершённых трансляций. Запись идущего эфира существует с его первых секунд и растёт до конца, поэтому по ней MUST определяться, что эфир ещё идёт, и такая запись MUST пропускаться до его окончания.
- **FR-004**: Владелец MUST иметь возможность добавить конкретную трансляцию в работу вручную по её адресу.
- **FR-005**: Система MUST распознавать уже разобранную трансляцию и не обрабатывать её повторно.
- **FR-006**: Система MUST пропускать записи, доступные только подписчикам, фиксируя причину пропуска, и не возвращаться к ним автоматически.
- **FR-007**: Система MUST сохранять сведения о трансляции: название, дату и время эфира, длительность, адрес записи, категории с временными границами.

**Расшифровка**

- **FR-008**: Система MUST преобразовывать речь из записи в текст с временными метками не грубее уровня отдельных фраз.
- **FR-009**: Система MUST определять язык речи и сохранять его вместе с трансляцией.
- **FR-010**: Расшифровка MUST оставаться служебным материалом: она не хранится после разбора и не выдаётся клиентам.
- **FR-011**: Система MUST выдерживать трансляции длительностью не менее 12 часов.

**Документ о трансляции**

- **FR-012**: Система MUST превращать расшифровку в связный человекочитаемый документ о трансляции, а не в набор отдельных реплик.
- **FR-013**: Модель, составляющая документ, MUST видеть расшифровку целиком, чтобы отсылки внутри эфира сохраняли смысл.
- **FR-014**: Документ MUST быть разбит на разделы по темам, каждый со своим заголовком, временем начала и категорией трансляции на этот момент.
- **FR-015**: Раздел MUST быть понятен без чтения соседних разделов и без доступа к записи.
- **FR-016**: Содержание документа MUST опираться только на прозвучавшее в записи; добавление сведений, отсутствующих в расшифровке, запрещено.
- **FR-017**: Система MUST пропускать участки без внятной речи и не создавать по ним разделы.
- **FR-018**: Документ MUST сохраняться целиком и быть доступным для чтения человеком.
- **FR-019**: Система MUST покрывать документом весь эфир: разрыв во времени между разделами, означающий пропущенный кусок, недопустим.

**Выдача знаний**

- **FR-020**: Система MUST предоставлять внешним программным клиентам способ запросить знания по произвольному тексту вопроса.
- **FR-021**: Поиск MUST находить знания по смысловой близости к запросу, а не только по совпадению слов.
- **FR-022**: Ответ MUST содержать для каждого результата: текст раздела целиком, тему, название и дату трансляции, категорию, временную метку и оценку релевантности.
- **FR-023**: Клиент MUST иметь возможность задать число результатов и ограничить выборку диапазоном дат и категорией.
- **FR-024**: Система MUST возвращать явный признак отсутствия знаний, когда ни один раздел не проходит порог смысловой близости.
- **FR-025**: Ответ MUST быть пригоден для прямой подстановки в контекст ИИ-ассистента: предсказуемая структура, без служебного мусора и обрезанных текстов.
- **FR-026**: Система MUST отвечать на запросы по готовым знаниям независимо от того, идёт ли в этот момент разбор новой трансляции.
- **FR-027**: Доступ к знаниям MUST быть публичным и не требовать авторизации.
- **FR-028**: Система MUST ограничивать частоту и объём обращений от одного источника, чтобы публичный доступ не приводил к исчерпанию ресурсов владельца.

**Видимость и управление**

- **FR-029**: Система MUST показывать человеку список разобранных трансляций с названием, датой, категориями и числом разделов.
- **FR-030**: Система MUST показывать список пропущенных записей с причиной пропуска.
- **FR-031**: Система MUST давать человеку прочитать документ любой разобранной трансляции целиком.
- **FR-032**: Система MUST размещать на странице инструкцию по подключению базы знаний к ИИ-ассистенту с готовым адресом сервиса.
- **FR-033**: Владелец MUST иметь возможность удалить трансляцию вместе с её документом и разделами.
- **FR-034**: Система MUST продолжать работу после сбоя, не теряя ранее разобранные трансляции.
- **FR-035**: Панель владельца MUST состоять из разделов со своими адресами, доступных из меню: о сервисе, подключение ассистента, справочник по запросам, знания, управление. Открытый раздел MUST быть доступен по прямой ссылке.
- **FR-036**: Система MUST описывать человеку, как обращаться к базе знаний: адреса запросов, примеры и коды ошибок.
- **FR-037**: Управляющие действия владельца MUST быть скрыты до предъявления верного токена: пока он не введён, человек видит только поле ввода токена и пояснение к нему.
- **FR-038**: Неверный токен владельца MUST отвергаться явной ошибкой, отличимой от его отсутствия.

### Key Entities *(include if feature involves data)*

- **Канал**: единственный отслеживаемый источник трансляций; имя, адрес, момент подключения.
- **Трансляция**: одна запись эфира; название, дата и время, длительность, адрес, язык, категории с временными границами, состояние разбора.
- **Документ трансляции**: связный текст о содержании эфира, состоящий из разделов; доступен человеку целиком.
- **Раздел**: часть документа с одной темой; заголовок, текст, время начала и окончания, категория; единица выдачи знаний.
- **Реестр**: перечень того, что разобрано и что пропущено, с причинами пропуска; основа списка на странице и признак «обрабатывать или нет».
- **Запрос знаний**: текст вопроса от клиента, наложенные ограничения и возвращённый набор разделов с оценками релевантности.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 9 случаях из 10 раздел, содержащий нужное знание, попадает в первые пять результатов запроса по действительно обсуждавшейся теме.
- **SC-002**: Ответ на запрос знаний приходит менее чем за 1 секунду при архиве в несколько сотен трансляций.
- **SC-003**: При выборочной проверке 20 разделов ни один не содержит утверждений, которых нет в записи, а временная метка расходится с реальным моментом не более чем на 10 секунд.
- **SC-004**: Не менее 95% разделов понятны проверяющему без просмотра записи и без чтения соседних разделов.
- **SC-005**: Запись четырёхчасового эфира становится доступной как знания не позднее чем через 2 часа после её появления, без участия человека.
- **SC-006**: Не менее 95% новых доступных записей канала доходят до состояния «знания доступны» без ручных действий.
- **SC-007**: Запросы обслуживаются во время разбора новых трансляций без отказов и без роста времени ответа более чем вдвое.
- **SC-008**: Разделы документа покрывают не менее 95% времени эфира, в котором звучит внятная речь.
- **SC-009**: Ни один сбой обработки не приводит к потере ранее разобранных трансляций.
- **SC-010**: Человек понимает содержание многочасовой трансляции по её документу менее чем за 3 минуты.
- **SC-011**: Владелец подключает базу знаний к своему ИИ-ассистенту по инструкции со страницы менее чем за 5 минут.

## Assumptions

- Потребитель знаний — программный ИИ-клиент; интерфейс для человека нужен, чтобы видеть содержимое базы, читать документы и подключить ассистента.
- Сервис отвечает знаниями, а не готовым ответом на вопрос: формулирование ответа остаётся за ИИ-клиентом.
- Отслеживается ровно один канал; поддержка нескольких вне охвата этой версии.
- Обрабатываются только записи прошедших эфиров; захват прямого эфира в реальном времени вне охвата.
- Расшифровывается речь со звуковой дорожки; чат трансляции, видеоряд и экранный текст не анализируются.
- Аудиозапись и расшифровка — временные данные: после разбора остаются только документ, разделы и сведения о трансляции.
- Категории трансляции берутся из данных площадки и не определяются по содержанию речи.
- Распознавание речи и составление документа выполняются внешними сервисами, доступ к которым обеспечивает владелец; их недоступность считается временной.
- Основной язык трансляций — русский или английский, определяется автоматически.
- Записи трансляций у источника живут ограниченное время, поэтому своевременность разбора важнее полноты исторического архива.
- Объём архива на горизонте года — сотни трансляций, а не десятки тысяч.
- Знания хранятся бессрочно и удаляются только по явному решению владельца.
