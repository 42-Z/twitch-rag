# Контракт: MCP-сервер базы знаний

**Дата**: 2026-09-13 | **Спецификация**: [spec.md](../spec.md) | **HTTP-контракт**: [knowledge-api.md](./knowledge-api.md)

Потребитель знаний — ИИ-ассистент. MCP даёт ему прямой способ пользоваться базой без
написания HTTP-клиента: ассистент видит инструменты и вызывает их сам.

Сервер — тонкая обёртка над тем же сервисом поиска, что обслуживает `POST /api/knowledge/search`.
Своей логики поиска у него нет; расхождение ответов между HTTP и MCP — дефект.

## Транспорт и запуск

- **stdio** — основной режим: ассистент запускает `bun run src/mcp/server.ts` как дочерний
  процесс. Ключи и адрес базы читаются из окружения приложения.
- Сервер работает поверх локального SQLite и Upstash напрямую, не требуя запущенного
  HTTP-сервера, поэтому знания доступны, даже когда операторский интерфейс не поднят.

Имя сервера — `twitch-knowledge`, версия берётся из `package.json`.

## Инструмент `search_knowledge`

**Описание для модели**: «Найти, что говорилось на стримах отслеживаемого канала.
Возвращает фрагменты знаний с темой, датой эфира и ссылкой на момент записи. Использовать,
когда вопрос касается мнений, решений, планов или событий, обсуждавшихся на стримах».

**Входная схема**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `query` | string | да | Вопрос или тема обычными словами |
| `topK` | integer | нет | Сколько документов вернуть, 1–20, по умолчанию 5 |
| `from` | string | нет | Не раньше этой даты эфира (YYYY-MM-DD) |
| `to` | string | нет | Не позже этой даты эфира (YYYY-MM-DD) |

**Результат**: текстовое содержимое, готовое к чтению моделью, — по одному блоку на
документ:

```
[1] Причины перехода на новый движок — «Пятничный разбор кода», 14.03.2026, 1:12:30
https://www.twitch.tv/videos/2345678901?t=1h12m30s
На стриме ведущий объяснил, почему команда уходит со старого движка: ...

[2] ...
```

Дополнительно в `structuredContent` возвращается тот же набор, что отдаёт HTTP API
(`documents[]` с полями `id`, `topic`, `text`, `score`, `stream`, `startSeconds`,
`endSeconds`), чтобы клиент мог разобрать ответ программно.

**Когда знаний нет** — не ошибка, а обычный ответ: «В базе знаний нет сведений по этому
вопросу». Модель должна сказать об этом пользователю, а не додумывать (FR-024).

**Ошибки** возвращаются как `isError: true` с текстом причины: недоступность Upstash,
исчерпанная квота OpenAI на эмбеддинг запроса, пустой запрос.

## Инструмент `knowledge_stats`

**Описание для модели**: «Узнать границы базы знаний: какой канал, сколько трансляций и
за какой период уже разобрано. Использовать, чтобы честно ответить, есть ли у ассистента
сведения о нужном периоде».

Параметров нет. Возвращает то же, что `GET /api/knowledge/stats`, в человекочитаемом виде
и в `structuredContent`.

## Ресурсы

`twitch-knowledge://streams` — список готовых трансляций (идентификатор, название, дата,
число документов). Позволяет ассистенту сослаться на конкретный эфир, не выполняя поиск.

## Правила

- Инструменты только читают. Запуск обработки, удаление и смена канала через MCP
  недоступны — это операторские действия, они остаются в HTTP API и интерфейсе.
- Тексты описаний инструментов пишутся для модели, а не для человека: они определяют,
  когда ассистент обратится к базе.
- Ответ инструмента не содержит служебных полей, идентификаторов векторов и отладочных
  данных — только то, что имеет смысл в контексте разговора (FR-025).
