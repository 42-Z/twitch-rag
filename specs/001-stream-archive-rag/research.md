# Исследование: База знаний канала по записям стримов

**Дата**: 2026-09-13 | **Спецификация**: [spec.md](./spec.md)

Все решения ниже проверены по официальной документации; ссылки приведены. Факты, которых в
документации нет, помечены явно — на них строятся допущения, а не утверждения.

## 1. Получение записей с Twitch

### Решение: опрос Helix `Get Videos` по расписанию, скачивание через yt-dlp

**Обнаружение новых трансляций**: `GET https://api.twitch.tv/helix/videos?user_id=...&type=archive&sort=time&first=100`
с заголовками `Client-Id` и `Authorization: Bearer <app access token>`. Токен — Client
Credentials flow (`POST https://id.twitch.tv/oauth2/token`), скоупы не нужны, срок жизни
берётся из `expires_in` ответа (в примере документации ~58 дней), обновление по 401.
Опрос раз в 15 минут через `Bun.cron`.

Ключевые поля ответа: `id`, `stream_id` (у архивных VOD равен id стрима — естественный ключ
дедупликации), `title`, `published_at` (RFC3339), `url`, `duration` (собственный формат
Twitch вида `1h2m3s`, не ISO 8601 — парсится регулярным выражением), `language`,
`muted_segments[]` (`{offset, duration}` — участки, заглушённые системой распознавания
музыки).

**Рациональность**: официального способа узнать о появлении VOD не существует — в списке
типов подписок EventSub нет ни одного, связанного с записями. Опрос по расписанию решает
задачу без OAuth-флоу с участием пользователя.

**Отвергнутые альтернативы**:

- **EventSub `stream.offline` + WebSocket-транспорт.** Не даёт события о VOD напрямую:
  всё равно нужен опрос `Get Videos` после окончания эфира. Требует user access token
  (app-токен с WebSocket-транспортом не работает), то есть проход Authorization Code flow и
  хранение refresh-токена, плюс обработка `session_reconnect` и keepalive. Цена сложности
  не окупается: задержка опроса в 15 минут для архива несущественна. Остаётся как
  возможное улучшение, если понадобится реакция в момент окончания эфира.
- **EventSub webhook-транспорт.** Требует публичный HTTPS на 443 порту — для локального
  приложения неприменимо.

**Ограничения, влияющие на продукт**:

- Twitch хранит записи ограниченное время: 60 дней для partner/Prime/Turbo, 14 дней для
  affiliate, 7 дней для остальных; хранение записей вообще должно быть включено стримером.
  `broadcaster_type` из `Get Users` даёт partner/affiliate/пусто, Prime и Turbo через API
  не определяются. Безопасная стратегия — считать окно равным 7 дням и не откладывать
  обработку: пропущенная запись исчезает навсегда.
- Рейт-лимит Helix — token bucket, 1 point за запрос; точное значение бакета в
  документации не зафиксировано, читается из заголовков `Ratelimit-Limit`,
  `Ratelimit-Remaining`, `Ratelimit-Reset`. При нашем одном запросе раз в 15 минут запас
  многократный.
- Задержка между окончанием эфира и появлением VOD в `Get Videos` в документации не
  описана — обнаружение строится на периодическом опросе, а не на ожидании.

Источники: [Get Videos](https://dev.twitch.tv/docs/api/reference/#get-videos),
[Get Users](https://dev.twitch.tv/docs/api/reference/#get-users),
[Client Credentials](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#client-credentials-grant-flow),
[Rate limits](https://dev.twitch.tv/docs/api/guide/#twitch-rate-limits),
[EventSub subscription types](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/),
[VOD storage](https://help.twitch.tv/s/article/video-on-demand).

### Решение: аудио через `yt-dlp -f bestaudio` в конвейере с ffmpeg

Официального API для скачивания VOD нет (в разделе Videos только `Get Videos` и
`Delete Videos`; endpoint выдачи ссылок существует только для клипов). yt-dlp поддерживает
Twitch экстракторами `twitch:vod`, `twitch:videos`, `twitch:stream`, и Twitch отдаёт
отдельный аудиорендишен (`Audio_Only`, AAC ~218 kbps, ~93 МБ/час) — скачивать видео не
требуется.

Конвейер без промежуточного файла:

```bash
yt-dlp -f bestaudio --no-part -o - "https://www.twitch.tv/videos/<ID>" \
| ffmpeg -i pipe:0 -vn \
    -c:a libopus -b:a 16k -ac 1 -ar 16000 -application voip \
    -f segment -segment_time 600 -reset_timestamps 1 \
    -segment_list chunks/index.csv -segment_list_type csv \
    chunks/chunk_%04d.opus
```

`segment_list_type csv` даёт строки `chunk_0000.opus,0.000000,600.000000` — готовые
смещения для приведения таймкодов куска ко времени всей трансляции.

**Параметры и их обоснование**:

| Параметр | Значение | Почему |
|----------|----------|--------|
| Кодек | opus, 16 kbps, моно, 16 кГц | час речи ≈ 6.8 МБ (замер), 4 часа ≈ 27 МБ — трафик и место перестают быть проблемой |
| Длина куска | 10 минут | ~1.1 МБ на кусок при лимите 25 МБ; 24 запроса на 4-часовой эфир, каждый быстрый, прогресс виден пользователю |
| Перекрытие | 5 секунд | документация OpenAI прямо предупреждает: не резать посреди фразы |

**Отвергнутые альтернативы**: streamlink (не умеет выбирать аудиодорожку, аудио всё равно
отделять через ffmpeg); нарезка «по 25 МБ» (в 25 МБ opus влезает почти 4 часа — один
запрос был бы долгим, непрозрачным по прогрессу и грубым по гранулярности).

**Ограничения**: публичные VOD скачиваются без авторизации (проверено); записи только для
подписчиков требуют cookies залогиненного пользователя и в этой версии не поддерживаются —
такая запись завершается понятной ошибкой. Официального разрешения Twitch на массовое
скачивание нет: проект рассчитан на свой канал или канал, давший согласие, и не сохраняет
исходное аудио.

Источники: [yt-dlp README](https://github.com/yt-dlp/yt-dlp#readme),
[ffmpeg segment muxer](https://ffmpeg.org/ffmpeg-formats.html#segment_002c-stream_005fsegment_002c-ssegment),
[ffmpeg options](https://ffmpeg.org/ffmpeg.html), [streamlink Twitch plugin](https://streamlink.github.io/cli/plugins/twitch.html).

## 2. Распознавание речи

### Решение: `whisper-1` с `response_format: "verbose_json"` и `timestamp_granularities: ["segment"]`

Это решение продиктовано единственным жёстким фактом: **таймкоды поддерживает только
`whisper-1`**. Документация формулирует прямо: «The `timestamp_granularities[]` parameter is
only supported for `whisper-1`». Рекомендованная и более дешёвая `gpt-transcribe`
($0.0045/мин против $0.006/мин) возвращает только текст.

Без таймкодов невозможны FR-015 (время начала разговора в документе), SC-003 (расхождение
не более 10 секунд) и весь смысл ссылки на момент записи. Смещение куска (10 минут) как
единственный источник времени дало бы точность ±10 минут — это не выполняет SC-003.

```ts
const transcription = await client.audio.transcriptions.create({
  file: Bun.file(chunkPath),                    // BunFile входит в тип Uploadable
  model: "whisper-1",
  response_format: "verbose_json",
  timestamp_granularities: ["segment"],
  language: "ru",                               // если язык канала известен
  prompt: tailOfPreviousChunk,                  // до 224 токенов
});
```

Ответ содержит `duration`, `language`, `text` и `segments[]` с полями `start`, `end`,
`text`, `avg_logprob`, `no_speech_prob` — последние два дают меру уверенности для FR-017 и
поля `confidence`.

**Гранулярность `segment`, не `word`**: документы строятся из фраз, пословные таймкоды
увеличивают объём ответа в разы без пользы для задачи.

**Передача контекста между кусками**: `prompt` — документированный сценарий «carrying
context from a previous chunk of a longer recording», лимит 224 токена для `whisper-1`.
Передаётся хвост текста предыдущего куска.

**Отвергнутые альтернативы**:

- `gpt-transcribe` — дешевле и точнее, но без таймкодов. Остаётся кандидатом, если OpenAI
  добавит их: переход изолирован в одном модуле.
- `gpt-4o-transcribe-diarize` с `diarized_json` — даёт `start`/`end` по репликам говорящих,
  но стоит как whisper-1, требует `chunking_strategy` для аудио длиннее 30 секунд и решает
  ненужную задачу (разделение говорящих).
- Локальный whisper.cpp — снимает расходы на API, но требует моделей, GPU и отдельного
  сопровождения; противоречит указанию использовать библиотеку OpenAI.

**Ограничения**: файл до 25 МБ (наши куски ~1.1 МБ), форматы `mp3, mp4, mpeg, mpga, m4a,
wav, webm`. **Важно: `opus` в списке принимаемых форматов отсутствует** — куски пишутся в
контейнер, который API принимает: `-c:a libopus -f ogg` не подойдёт, используется
`-c:a libmp3lame -b:a 32k -ac 1 -ar 16000` (13.8 МБ/час, ~2.3 МБ на 10-минутный кусок) либо
opus в контейнере `webm` (`-c:a libopus -f webm`). Выбран **webm/opus**: вдвое компактнее
mp3 при том же качестве речи и входит в список поддерживаемых форматов.
Максимальная длительность файла в документации не указана — ограничение только по размеру.

Источники: [Speech to text](https://developers.openai.com/api/docs/guides/speech-to-text),
[Transcription guide](https://developers.openai.com/api/docs/guides/transcription),
[Pricing](https://developers.openai.com/api/docs/pricing).

## 3. Структурирование расшифровки в документы

### Решение: Responses API + Structured Outputs через `zodTextFormat`, модель `gpt-5.6-luna`

```ts
const response = await client.responses.parse({
  model: "gpt-5.6-luna",
  input: [
    { role: "system", content: STRUCTURING_INSTRUCTIONS },
    { role: "user", content: windowText },
  ],
  text: { format: zodTextFormat(KnowledgeWindow, "knowledge") },
});
const documents = response.output_parsed.documents;
```

**Почему Responses API**: документация прямо рекомендует его для новых проектов («While
Chat Completions remains supported, Responses is recommended for all new projects»), он же
даёт лучшее попадание в кэш промпта.

**Почему `gpt-5.6-luna`**: контекст 1 050 000 токенов при цене $0.20 за 1M входных и $1.20
за 1M выходных токенов — на порядок дешевле старших моделей при задаче, которая по сути
является переписыванием и разметкой текста. Эскалация на `gpt-5.6-terra` ($2.00/$12.00)
предусмотрена настройкой, если качество документов окажется недостаточным.

**Обработка длинной расшифровки**: официального рецепта map/reduce в документации нет.
Решение: расшифровка режется на окна по ~20 минут речи по границам сегментов, каждое окно
обрабатывается отдельным запросом с передачей темы предыдущего окна в системном сообщении;
окна обрабатываются с ограничением параллельности. Это даёт короткие ответы (вместо упора
в 128 000 выходных токенов), прогресс по окнам и устойчивость: сбой одного окна не рушит
всю трансляцию. Дополнительный довод — цена: у моделей GPT-5.6/GPT-6 запрос длиннее 272K
входных токенов тарифицируется по удвоенной ставке целиком.

**Ограничения JSON Schema, которые определяют форму схемы**:

- `additionalProperties: false` в каждом объекте, все поля в `required`; опциональность —
  только через `["string", "null"]`, то есть в Zod `.nullable()`, а не `.optional()`;
- корень схемы — объект, не `anyOf`: дискриминированные union'ы на верхнем уровне не
  работают;
- из строковых ограничений поддерживаются только `pattern` и `format`, `minLength`/
  `maxLength` не поддерживаются — длину текста документа проверяет наш код, а не схема;
- до 5000 свойств, 10 уровней вложенности.

**Обязательная обработка двух случаев**: поле `refusal` в выводе (модель отказалась —
схема не соблюдена) и `status: "incomplete"` при упоре в `max_output_tokens`. Оба
превращаются в повтор с меньшим окном, а после трёх неудач — в понятную ошибку этапа.

**Отвергнутые альтернативы**: Chat Completions с `response_format` (поддерживается, но не
рекомендуется для новых проектов); `truncation: "auto"` для длинного входа (молча
отбрасывает начало — недопустимо, знания теряются без следа); Batch API (−50% к цене, но
гарантия только 24 часа — противоречит SC-005 «доступно не позднее чем через 2 часа»).

Источники: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs),
[Migrate to Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses),
[Pricing](https://developers.openai.com/api/docs/pricing), [Batch](https://developers.openai.com/api/docs/guides/batch).

## 4. Эмбеддинги и векторный поиск

### Решение: `text-embedding-3-small` (1536) + плотный индекс Upstash Vector

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Модель | `text-embedding-3-small` | $0.02 за 1M токенов, 1536 измерений, до 8192 токенов на вход |
| Размерность индекса | 1536 | бесплатный тариф Upstash Vector ограничен 1536 измерениями; `-3-large` (3072) требует платного плана без выигрыша, оправдывающего его для русскоязычной речи |
| Метрика | COSINE | стандарт для эмбеддингов OpenAI |
| Тип индекса | DENSE | см. ниже |
| Батч | до 96 документов за запрос | лимиты API — 2048 элементов и 300 000 токенов суммарно; 96 держит запрос быстрым |

**Хранение**: текст документа — в поле `data` вектора, фильтруемые атрибуты — в
`metadata` (лимит 48 КБ на вектор). Идентификатор `{vodId}:{docIndex}` позволяет заменять
и удалять все документы трансляции по префиксу.

**Отвергнутые альтернативы**:

- **Гибридный индекс (dense + sparse BM25)** — точнее находил бы имена, термины и названия.
  Но встроенные модели Upstash (`BGE_*`, `BM25`) и собственные векторы в документации
  описаны как два отдельных сценария; возможность сочетать свой dense-вектор от OpenAI с
  hosted sparse-моделью документацией не подтверждена, а гибридный индекс требует
  обязательно оба вектора при каждом upsert. Собственный BM25 — отдельная задача с
  собственным словарём. Отложено до появления подтверждённой поддержки или реальной
  потребности.
- **Встроенные модели эмбеддингов Upstash** — убрали бы расход на OpenAI, но модели
  ориентированы на английский, а канал русскоязычный; и это противоречит указанию
  использовать OpenAI для обработки.
- **Upstash Search** — продукт для полнотекстового поиска; задача требует именно векторного
  поиска по смыслу.

**Лимиты тарифа**: бесплатный — 200M векторов×измерений, 10 000 запросов в день, 1 ГБ;
метаданные до 48 КБ на вектор; `topK` до 1000. Для сотен трансляций (десятки тысяч
документов) бесплатного тарифа достаточно, платный включается без изменения кода.

Источники: [Embeddings](https://developers.openai.com/api/docs/guides/embeddings),
[Vector pricing & limits](https://upstash.com/pricing/vector),
[Hybrid indexes](https://upstash.com/docs/vector/features/hybridindexes), скилл `upstash-vector-js`.

## 5. Временное хранение аудио

### Решение: Upstash Blob, приватный бакет, объекты живут до конца обработки

Куски аудио кладутся в `audio/{vodId}/part-{NNN}.webm` и удаляются сразу после успешной
транскрипции куска; при любом завершении обработки выполняется удаление по префиксу.
Ежесуточная уборка удаляет объекты старше суток и незавершённые multipart-загрузки
(`abortStaleMultipartUploads`).

**Зачем вообще внешнее хранилище**, если аудио можно держать на диске: обработка
восстанавливается после перезапуска процесса и переезда приложения (в том числе в
контейнере без постоянного тома), а диск оператора не забивается гигабайтами при сбое.
Расход мизерный: 4-часовой эфир — около 27 МБ, которые живут считанные часы.

**SDK**: `@upstash/blob` (`bucket.put`, `bucket.get`, `bucket.del({ prefix })`). Версия на
момент планирования — 0.0.5 (опубликована 2026-09-07), это ранний SDK: весь код работы с
хранилищем изолируется в одном модуле, а запасной путь — встроенный в Bun `S3Client`
(бакеты S3-совместимы, временные ключи выдаёт `upstash blob credentials`), переход не
затрагивает остальной код.

**Тариф**: бесплатно 1 ГБ хранения, 10 000 простых и 2000 «продвинутых» операций в месяц,
10 ГБ исходящего трафика. Загрузка — «продвинутая» операция: 24 куска на эфир, то есть
около 80 эфиров в месяц укладываются в бесплатный лимит; при превышении — $4.50 за 1M
операций.

Источники: [Upstash Blob](https://upstash.com/docs/blob), [Blob pricing](https://upstash.com/pricing/blob),
скиллы `upstash-blob-js`, `upstash-cli`.

## 6. Среда выполнения и локальное состояние

| Решение | Обоснование |
|---------|-------------|
| **Bun 1.4 + TypeScript** | требование проекта; в системе стоит 1.4.0 |
| **`Bun.serve()` с `routes`** и HTML-импортом | один процесс отдаёт и API, и операторский интерфейс; HMR в разработке |
| **`bun:sqlite`** для состояния | очередь, статусы, журнал, лог запросов должны переживать перезапуск; внешняя БД для одного пользователя избыточна. WAL-режим включается для параллельного чтения интерфейсом во время записи воркером |
| **`Bun.cron`** для планировщика | встроенный планировщик: опрос Twitch раз в 15 минут, уборка Blob раз в сутки — без внешних зависимостей |
| **`Bun.spawn` / `Bun.$`** для yt-dlp и ffmpeg | потоковая передача между процессами, контроль кода возврата и stderr |
| **WebSocket из `Bun.serve()`** | прогресс обработки в интерфейсе без опроса |
| **`@modelcontextprotocol/sdk` 1.30** | подключение базы знаний к ИИ-ассистенту как MCP-сервера через stdio |

Внешние зависимости процесса: `yt-dlp` (в системе 2026.07.04) и `ffmpeg` (9.0.1) — их
наличие проверяется при старте и отражается в `/api/health`, отсутствие даёт понятную
ошибку, а не падение в середине обработки.

**Отвергнутые альтернативы**: очередь на QStash/Upstash Workflow (требует публичного URL
для доставки сообщений — для локального приложения неприменимо); хранение состояния в
Upstash Redis (добавляет сетевую зависимость в путь, который обязан работать и при
недоступности сети); внешний планировщик (systemd timer, cron) — усложняет запуск в
контейнере.

## 7. Расхождение со спецификацией: судьба расшифровки

`CLAUDE.md` проекта задаёт: «Расшифровка и запись не сохраняется». Спецификация же в FR-010
и FR-033 предполагала хранение расшифровки ради повторного структурирования без повторного
скачивания.

**Решение**: следовать `CLAUDE.md`. Расшифровка существует только в памяти процесса между
этапами транскрипции и структурирования и нигде не сохраняется. Повторное структурирование
(FR-033, US4) выполняется как полная переобработка: скачивание → транскрипция →
структурирование → индексация. Пользовательская функция сохраняется полностью, меняется
только её цена и длительность.

**Следствия**: SC-010 («повторное структурирование не требует повторного скачивания и
выполняется быстрее первичной обработки») не выполняется и подлежит замене при следующей
правке спецификации; в остальном FR-010/FR-011 переформулируются как «расшифровка не
покидает память процесса». Записи старше срока хранения Twitch переобработать невозможно —
интерфейс предупреждает об этом до запуска.
