# Приёмочные проверки

**Спецификация**: [spec.md](./spec.md) | **План**: [plan.md](./plan.md)

Эти сценарии выполняются **после выпуска**, на боевом сервисе, и в список задач не
входят: без развёрнутого сервиса и настоящей записи их выполнить нельзя.

Порядок выпуска перед проверками — [contracts/pipeline.md](./contracts/pipeline.md):
сначала программа конвейера в машину, потом слияние в основную ветку.

## 1. Зависшая запись разбирается до конца

Запись `2878430068` (5 ч 47 мин) — та, на которой всё сломалось. Она короче порога,
поэтому делиться не должна, но обязана пройти на новой нарезке.

```sh
# снять залипание и отправить на повторный разбор
curl -X POST -H "x-app-admin-token: $APP_ADMIN_TOKEN" \
  https://twitch-rag.crbanana.workers.dev/api/streams/2878430068/reparse
```

Ожидается: одна запись без суффикса части, разбор доходит до конца, документ доступен по
`/api/streams/2878430068/document`, в базе знаний есть фрагменты из первого и последнего
часа эфира. В журнале Worker нет строк `Too many subrequests`.

Счёт обращений при этом — 33 из 50 ([research §2](./research.md)).

## 2. Длинный эфир делится

Нужна запись длиннее шести часов. Если канал такой ещё не дал, годится любая длинная
запись, добавленная владельцем вручную.

Ожидается:

- в реестре появляются записи `<vodId>-p1`, `<vodId>-p2`, … — по одной на часть;
- каждая часть разбирается своим прогоном и даёт свой документ;
- части идут в списке подряд и по порядку эфира;
- сумма длительностей частей равна длительности эфира, дыр между ними нет.

## 3. Ссылка из второй части ведёт в нужное место

Найти в поиске по знаниям фрагмент, заведомо относящийся ко второй части (например, по
теме, которая звучала в конце эфира), и открыть ссылку.

Ожидается: площадка открывается на нужном моменте эфира. Промах на длину первой части
означает, что смещение потерялось.

## 4. Отказ одной части не трогает другие

Дождаться естественного отказа или вызвать его повторным разбором части при недоступном
внешнем сервисе.

Ожидается: у сорвавшейся части растёт число попыток и появляется причина, у остальных
частей документы и знания на месте, число фрагментов в базе по ним не уменьшилось.

## 5. Повторный разбор одной части

```sh
curl -X POST -H "x-app-admin-token: $APP_ADMIN_TOKEN" \
  https://twitch-rag.crbanana.workers.dev/api/streams/<vodId>-p2/reparse
```

Ожидается: разбирается только эта часть, её прежние фрагменты в базе знаний заменяются
новыми, документ первой части не меняется.

## 6. Старые записи не пострадали

Открыть документ записи, разобранной до выпуска (`2877527009` или `2876609843`), и найти
её фрагмент в поиске.

Ожидается: документ открывается по прежнему адресу, фрагменты находятся, ссылки работают.
Ничего не переразбиралось.

## 7. Часовая проверка берёт следующую часть

Дождаться следующего часа после разбора первой части длинного эфира.

Ожидается: проверка берёт вторую часть того же эфира, а не следующую запись архива —
база растёт по порядку эфиров.

## Признаки беды

- `Too many subrequests` в журнале Worker — лимит снова достигнут, порог или нарезку
  надо пересчитать по формуле [research §2](./research.md).
- Отказ распознавания по таймауту — провайдер отвечает медленнее, чем при замере;
  двадцатиминутный кусок стал слишком длинным.
- Записи частей стоят в списке вразнобой — время начала части посчитано неверно.
